# 交付物模式

同一批材料可以形成不同文种。先选模式，再决定结构和密度。

## 架构提案 / 汇报主文档

适用于方向对齐、争取资源、组内分享和现场讲述。

- 核心问题：为什么值得做、我们判断什么、准备怎么证明；
- 开场：业务变化、真实案例或能力缺口；
- 主体：目标架构、路线取舍、阶段验证和合作价值；
- 视觉骨架：问题与机会、技术判断、目标架构、训练或数据闭环、路线与验收；
- 结尾：希望当场形成的共识或决定；
- 附件：论文、完整实验、任务 Map、RACI、Gate 和资源表。

警惕：用授权边界、工作包和签字条件开场；把所有反方质疑提前塞入正文。

## 技术设计稿

适用于方案已经基本确定，需要工程或算法团队实现。

- 核心问题：系统如何工作，接口、状态和失败处理是什么；
- 开场：目标、约束和非目标；
- 主体：组件、数据流、接口、算法、兼容性、可靠性与迁移；
- 视觉骨架：系统上下文、组件架构、关键数据流或时序、失败与降级路径；
- 结尾：未决设计点和实现计划。

警惕：只讲愿景而没有接口；把待验证方向伪装成已确定设计。

## 架构决策记录

适用于记录一个已经讨论过的关键取舍。

- 核心问题：为什么选择 A 而不是 B；
- 主体：背景、决策驱动因素、候选项、证据、决定和后果；
- 视觉骨架：候选路线、关键差异、证据链和决策后影响；
- 结尾：复审条件与可逆性。

警惕：重新讲完整项目历史；只保留结论而没有取舍证据。

## 执行计划 / 治理合同

适用于方向已经对齐，需要冻结责任、资源和时间。

- 核心问题：谁在何时交付什么，如何验收和降级；
- 主体：工作包、依赖、Gate、RACI、资源、风险和升级路径；
- 视觉骨架：关键路径、依赖关系、阶段 Gate 和资源释放；
- 结尾：签字项和启动条件。

警惕：在方向尚未形成共识前就分配责任；用流程完备性替代技术可行性。

## 组合交付

复杂项目通常同时需要上述材料，但应拆层：

1. 架构提案负责被讲述和形成共识；
2. 技术设计与决策记录回答专业追问；
3. 执行计划在方向确认后生效。

可以相互链接，不要把三种文种压缩成一份超长正文。
